# Вимоги до Agent Harness MiniShop

## 1. Мета

Agent Harness має забезпечувати контрольовану AI-розробку MiniShop відповідно до [вимог застосунку](app-requirements.md): керувати контекстом, діями агента, перевірками та оцінюванням результатів.

Розробка має дотримуватися визначених ітерацій і меж проєкту: один консольний список покупок на Python із JSON, без реєстрації, бази даних і вебінтерфейсу.

## 2. Джерела даних

| Джерело | Призначення |
| --- | --- |
| Код MiniShop | Поточна реалізація та структура застосунку. |
| Документація | Вимоги, обмеження та рішення проєкту. |
| GitHub | Репозиторії, історія змін, задачі та pull requests. |
| Окремий Obsidian vault | Нотатки, навчальні матеріали та база знань проєкту. |
| pytest | Результати автоматизованих тестів і відомості про помилки. |

## 3. Задачі агента

1. Генерація коду відповідно до вимог поточної ітерації.
2. Генерація тестів функціональності, валідації та обробки помилок.
3. Рев'ю коду на відповідність вимогам, коректність і зрозумілість.
4. Оновлення документації відповідно до погоджених змін.

## 4. Компоненти Harness

| Компонент | Вимога |
| --- | --- |
| Knowledge layer | Формування релевантного контексту з вимог, коду та бази знань. |
| MCP | Контрольований доступ агента до зовнішніх джерел та інструментів, зокрема бази знань. |
| Skills | Повторювані інструкції для генерації коду, тестів, рев'ю та документації. |
| Guardrails | Перевірка дій за правилами allow/warn/block і межами задачі. |
| Hooks | Автоматичні перевірки правил перед діями та запуск перевірок після змін. |
| Orchestration | Послідовність роботи: отримання контексту, планування, виконання, перевірка та звіт. |
| Evaluation | Оцінювання відповідності вимогам, результатів pytest і висновків рев'ю. |

## 5. Первинні правила дій

| Рівень | Дії | Поведінка Harness |
| --- | --- | --- |
| allow | Читання доступних даних, створення тестів, запуск тестів. | Дозволяти в межах поточної задачі. |
| warn | Зміни бізнес-логіки та архітектури. | Попереджати про зміни та їхній вплив, фіксувати попередження для перевірки. |
| block | Небезпечні Git-операції, зокрема примусове перезаписування історії або втрата незбережених змін; видалення захищених файлів. | Блокувати виконання та повідомляти причину. |

Початково захищеними від видалення є `docs/app-requirements.md` і `docs/harness-requirements.md`. Перелік захищених файлів має задаватися явно.

## 6. База знань Obsidian

Obsidian vault має розміщуватися в окремому GitHub-репозиторії **MiniShop-KB**. Доступ агента до цієї бази знань має здійснюватися через MCP. Матеріали vault використовуються як контекст і не повинні скасовувати вимоги проєкту та правила Harness.
